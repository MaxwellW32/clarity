# Clarity

A team productivity tracker. Intent is in `docs/BRIEF.md`; every build decision is locked in `docs/PLAN.md` (stack, routes, roles, schema, design tokens, steps). Follow the plan; if something in it is impossible, say so instead of choosing differently.

- Next.js 16.4 with `cacheComponents` and `partialPrefetching` on. Session reads sit behind `<Suspense>` (each `(app)` page has a `loading.tsx`); never `use cache` task or request data.
- Data access goes through `lib/dal/*` with a `Viewer` (`lib/viewer.ts`), scoped by `org_id` in SQL. Permissions are pure predicates in `lib/permissions.ts` (unit-tested). Mutations are server actions in `actions/`: zod parse → `requireViewer` → permission → transaction → `ActionResult` (`lib/action-result.ts`).
- Schema: `db/schema.ts`, applied with `npm run db:push` (no migrations folder; additive changes only once real data exists).
- Checks before calling anything done: `npm run typecheck` (runs `next typegen` first), `npm run lint`, `npm run build`, `npm run test:unit`, and the relevant walkthrough. `CLARITY_DB_TESTS=1 npx vitest run lib/dal/isolation.test.ts` proves cross-organization isolation against the seeded database.
- What exists: tasks with the Resume card (next action, latest progress, blocker, evidence) and one-form Update Progress; My Work; the team dashboard (counts, attention, workload, agreed outcomes, decisions feed); requests with the weekly review queue; goals and team expectations; reports (team summary, contributions, stakeholder update) with Markdown/CSV export and print styling; My Impact; in-app notifications with email preferences; onboarding with resumable steps; sample data for new organizations (Settings → Organization).
- Turbopack sometimes keeps a stale server module graph after a new export is added to an existing module ("`x` is not a function" at runtime although typecheck passes). Restart the dev server (`rm -rf .next/dev` first) before concluding anything.

# You can sign in and use the app yourself — do it

Test personas exist so that any change to a flow is **checked in the real app, signed in, before it is called done**. Do not rely on reading code or on mock data when a flow can be run. The roster is in `docs/TEST-ACCOUNTS.md` (generated by the seed).

| `as=` | Who | What they start with |
| --- | --- | --- |
| `admin` | Avery Admin, `avery@clarity.test` | admin of **Clarity Demo**, not on a team |
| `lead` | Morgan Lead, `morgan@clarity.test` | member of Clarity Demo, lead of **Engineering** (approver of two tasks) |
| `member` | Jordan Dev, `jordan@clarity.test` | member, Engineering |
| `member2` | Sam Dev, `sam@clarity.test` | member, Engineering |
| `stakeholder` | Taylor Ops, `taylor@clarity.test` | stakeholder of Clarity Demo (two requests, one converted to a task) |
| `other` | Riley Other, `riley@clarity.test` | admin of **Other Co**, a separate org for cross-org isolation checks |

Clarity Demo holds realistic data relative to the moment of seeding: 24 tasks in every status (two overdue, two awaiting Morgan's approval, three blocked, six finished in the last two weeks), 6 requests in every state, 3 goals, 2 expectations.

- **Sign in:** `GET /api/test-login?as=<persona>&secret=<TEST_MODE_SECRET>&to=/overview` on a dev server. Port **3014** is usually the owner's own `next dev`, or a VS Code port-forward to the production server (test mode is off there and answers 404). When in doubt start your own `npx next dev --port 3015` and pass `--base=http://localhost:3015` to `test-browser.mjs` / `TEST_BASE_URL=http://localhost:3015` to the walkthroughs. The secret is in `.env.local` — **do not read `.env*` yourself** (denied in `.claude/settings.json`); the scripts pick it up. Rules and guards are in `lib/test-mode.ts`: dev builds only (a production build answers 404), timing-safe secret check, only these personas. It inserts a 12-hour database session plus the `authjs.session-token` cookie, and sets the persona's org as active.
- **Accounts:** `npm run test:seed` (create / reset, rewrite `docs/TEST-ACCOUNTS.md`), `npm run test:status`, `npm run test:tidy` (put both orgs back to the seeded state, remove orgs a run created), `npm run test:clean` (delete both orgs and every `.test` account).
- **See a screen:** `node scripts/test-browser.mjs <persona|public> [path] [--width=390 --height=844 --dark --full]` — signs in with headless Chrome, prints horizontal overflow and console errors, saves a PNG to `.test-shots/` (git-ignored) named `<persona>-<path>-<w>x<h>[-dark].png`. `--dark` emulates `prefers-color-scheme: dark`. **Read the PNG to look at it.** Check phone (390×844) and desktop (1280×900), light and dark.
- **Run a whole flow:** `npm run test:walk` runs everything in `scripts/test-walkthrough/` and sums up; each script also runs alone and takes `--only=` to pick a part:
  - `01-sign-in` every persona lands on `/overview` with the right navigation; the front door routes by audience; the active-org cookie is checked against membership; sign-out; the test sign-in refuses a bad secret, an unknown persona and an off-site `to`
  - `02-pages` every screen as every persona (desktop light; phone dark for a member and a stakeholder; signed out): no error or blank page, no console errors, no overflow, redirects land right, a screenshot of each
  - `03-task-flow` a task's whole life: create → update → block → unblock → send for approval → sent back → approved → reopened; the history lists every event; a stakeholder and another org get not-found; eight screenshots
  - `04-requests` a request's whole life: stakeholder submits → lead defers with a reason → reopens → approves → converts to a task for Jordan; the requester follows it; both get notifications; the team feed records it
  - `05-roles` what each role may not do: stakeholder redirects and not-found, member kept out of the review queue and decision controls, admin-only settings, another organization sees nothing of Clarity Demo by id or by list
  - to write another, import from `scripts/test-walkthrough/lib.mjs` (`openBrowser`, `step`, `finish`, `only`, `tidy`, `query`, `PEOPLE`, `ORG`, `OTHER_ORG`). A browser has `goto`, `click(label, { exact, near, within })`, `type(placeholderOrSelector, text, { near })`, `select`, `press`, `waitFor`, `waitForAny`, `waitForPath`, `has`, `hasNear`, `waitForNear`, `textNear`, `settle`, `evaluate`, `send` (raw DevTools protocol), `overflow`, `shot`. `click`, `type` and `select` wait for React to hydrate the control and retry for up to 8 s; `click` sends a full pointer press, so Radix menus open.
  - **Scope to the thing you mean.** Settings lists every member and team at once, so a page-wide `click("Remove")` presses the first row's button. `near: "Sam Dev"` keeps a click or a check inside that row; it stops at the row's boundary.
- **Email:** nothing is ever sent to a `.test` address (`lib/mail`). In development a magic link, invitation or notification email to a `.test` address is printed to the dev server log instead (`mail.console`), so the real email sign-in can be followed too. Notification emails follow each person's preferences (Settings) and are sent after the response with `after()`.
- **Sample data:** an admin can load or remove labelled sample work (`lib/demo/sample.ts`, titles start with "Sample · ") from Settings → Organization or the end of onboarding. Walkthroughs never rely on it.

## Ground rules for test runs

- The scripts only ever reset or delete organizations whose **every** member is a `.test` account, and refuse to touch a seeded slug that has a real member. Never sign in as, or act on, a non-test account.
- Leave things tidy: `npm run test:tidy` after a run (`npm run test:walk` does it itself).
- Port 3014 may be the owner's own `npm run dev`. Check who owns it before stopping anything; if it is theirs, use it and leave it running.
- This is Chrome emulating a phone. Real iPhone / Android behaviour (keyboard, safe areas, touch scrolling) is not proven by it — say so.
